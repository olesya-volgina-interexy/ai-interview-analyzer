# Руководство пользователя — AI Interview Analyzer

Приложение для автоматического анализа интервью с кандидатами через LLM. Позволяет отслеживать воронку найма, собирать аналитику по клиентам/ролям/менеджерам и автоматически получать анализы по тикетам из Linear.

## Общая навигация

**Верхняя панель (header):**
- Логотип **Interview AI** слева;
- Три вкладки: **Dashboard**, **Interviews**, **Candidates**;
- Кнопка **+ New Analysis** — открывает форму анализа вручную;
- **Селектор периода** (иконка календаря) — фильтрует метрики на Dashboard. Варианты: текущий месяц (по умолчанию), прошлый месяц, последние 3 месяца, год, произвольный диапазон.

> Селектор периода влияет **только на Dashboard**. На страницах Interviews и Candidates у каждой свои фильтры.

## Страница Dashboard

Главная страница с общей аналитикой за выбранный период.

### Верхний ряд KPI-карточек

| Карточка | Что показывает |
|---|---|
| **Total Interviews** | Общее число интервью за всё время + разбивка по стадиям (manager call / technical) |
| **Hire Rate** | Процент найма среди технических интервью |
| **Avg Score** | Средний AI-скор (0-100) среди технических интервью |
| **Top Role** | Наиболее часто анализируемая роль |

> KPI-блок всегда показывает all-time статистику и не реагирует на селектор периода — это «пульс» системы в целом.

### Вкладка **Overview**

Две диаграммы-распределения по всем интервью: bar-chart по ролям и pie-chart по стадиям.

### Вкладка **Pipeline**

Воронка найма за период:

- **Requests Stats** — количество входящих тикетов по статусам и по клиентам. Возможные статусы: `Triage`, `New`, `In Progress`, `Client Review`, `CV Sent`, `Manager Call`, `Technical`, `Hired`, `Rejected` / `Lost`, `On Hold`, `Dropped`. У шести самых частых (Hired, Technical, Manager Call, In Progress, New, Rejected, Lost) — фирменная окраска точки/полоски, у остальных серая. Внутри — две вкладки: **By Status** и **By Client**. Кнопка **Refresh** принудительно сбрасывает кэш и пересчитывает.
- **Pipeline Funnel** — столбчатая воронка CV Sent → Manager Call → Technical → Final Result → On Hold → Hired. Внизу: общее количество отправленных CV (`Total CVs` — сумма `cvSentCount` по тикетам периода) и две конверсии — `Manager Call → Technical` и `Technical → Hired`.
- **Time on Stages** — верхний акцентный блок показывает среднее время от появления тикета до найма (`Avg time from Triage to Hired`). Ниже — сегментированная полоса прогресса по стадиям (Triage / In Progress / Client Review / Broker's Call / Tech Call) с подписями времени в днях. Под ней — тренд количества интервью по месяцам.

### Вкладка **Quality & Insights**

- **Quality Insights** — четыре под-вкладки:
    - **Rejection reasons** — топ-кластеры `decisionBreakers` из всех интервью периода;
    - **Weaknesses** — топ-кластеры слабостей кандидатов;
    - **External reasons** — топ-кластеры внешнего фидбека от клиентов (`IncomingRequest.externalFeedback`);
    - **Hire rate by role** — процент найма по ролям с количеством интервью.
  Текстовые причины кластеризуются через LLM (`clusterTextItems`) — близкие по смыслу формулировки сворачиваются в одну с подсчётом частоты.
- **Avg Score by Role** — radar-диаграмма средних скоров по ролям.
- **Avg Score by Level** — карточки со средним скором по уровням Junior / Middle / Senior / Architect (на планшете укладывается в сетку 2×2).

### Блок **Recent Analyses**

5 последних интервью с кликабельными строками — открывают модалку с полным анализом.

## Страница Interviews

Полная история всех проведённых анализов интервью с фильтрами.

### Фильтры (строка сверху)

| Фильтр | Поведение |
|---|---|
| **Role** | Точное совпадение с ролью |
| **Level** | Junior / Middle / Senior / Architect |
| **Stage** | Manager Call / Technical / Final Result |
| **Decision** | Hired / Rejected / **Uncertain**. `Hired`/`Rejected` берутся из колонки `decision` в БД. `Uncertain` — это технические интервью, у которых LLM выставила `recommendation = 'uncertain'` внутри JSON-анализа (в БД нет ни «hired», ни «rejected», но в карточке отображается оранжевый бейдж Uncertain). |
| **Manager** | Выбор из реально встречавшихся имён менеджеров **+ опция Uncertain** — показывает интервью, где имя менеджера не было распознано (`managerName IS NULL`). На технической стадии менеджер сейчас не пишется, поэтому такие записи тоже попадают в `Uncertain`. |
| **Search by client...** | Подстроковый поиск по названию клиента (регистронезависимо) |
| **Clear** | Сбросить все фильтры |

### Таблица

Колонки: Date, Stage, Role, Client, Manager, Result (badge), Score. Сортировка по дате (свежие сверху). Клик по строке открывает модалку интервью.

## Страница Candidates

Список всех кандидатов с агрегированной статистикой.

### Поиск и фильтры

- **Search by name** — текстовый поиск по имени, c debounce 300 мс;
- **All Roles** — фильтр по роли, на которую кандидат проходил интервью;
- **All Results** — Hired (есть хоть один найм) / Not Hired (успешных найма нет);
- **Clear** — сбросить фильтры.

### Таблица

| Колонка | Смысл |
|---|---|
| **Candidate** | Имя |
| **Roles** | Роли, на которые кандидат проходил интервью (до 2 видно, остальные под «+N») |
| **Interviews** | Всего интервью (сортируемая колонка) |
| **Hired** | Сколько раз кандидат был нанят (в разных тикетах) |
| **Rejected** | Сколько раз получен отказ |

| **Last** | Дата последнего интервью (сортируемая колонка) |

**Пагинация:** 20 записей на страницу, кнопки Previous / Next.

> `Hired` / `Rejected` у кандидата считаются только по **финальной стадии** тикета (когда тикет в Linear переходит в `Hired` / `Lost`). Стадии Manager Call и Technical в этот счёт не идут до закрытия тикета.

## Создание анализа вручную («+ New Analysis»)

Кнопка в верхней панели открывает модалку с формой. Нужна для разовых анализов — когда в Linear анализ не был запущен автоматически.

### Поля формы

**Transcript** *(обязательно)*
Текстовое поле под транскрипт интервью (минимум 200 px высоты). Поддерживает drag-and-drop файла `.txt`.

**Interview Details** *(обязательно)*
- **Stage** — Manager Call / Technical;
- **Role** — Backend / Frontend / Fullstack / DevOps / QA / Mobile;
- **Level** — Junior / Middle / Senior / Architect;
- **Interviewer Decision** — появляется только при `Stage = Technical`: Hired / Rejected.

**Participants** *(опционально)*
- **Client Name** — название клиента;
- **Candidate Name** — имя кандидата (если не указать — возьмётся из CV/транскрипта);
- **Manager** — имя проводившего интервью.

**Дополнительно** *(опционально)*
- **Broker Request** — требования от брокера;
- **Interviewer Comments** — комментарии менеджера;
- **Linear Issue ID** — например, `ENG-123`, чтобы связать с тикетом в Linear.

### Запуск и прогресс

Кнопка **Start Analysis** запускает анализ. Появляется прогресс-экран с этапами:

1. Downloading CV;
2. Creating embedding;
3. Finding similar cases;
4. AI analysis;
5. Saving results;
6. Done.

По завершении — три кнопки:
- **New Analysis** — обнулить форму и начать заново;
- **Close** — закрыть модалку;
- **View in History →** — открыть страницу Interviews.

## Модалка интервью (Analysis, Transcript, CV, Questions)

Открывается кликом по строке в любой таблице (Dashboard → Recent Analyses, Interviews, Candidate Detail).

### Заголовок

Аватар с именем кандидата, роль, уровень, клиент, дата. Кнопки:
- **Save as PDF** — экспорт отчёта (печать);
- **Delete** — удалить запись (с подтверждением);
- **×** — закрыть.

### Вкладки (зависят от наличия данных)

**Analysis** — AI-оценка, форма зависит от стадии:

- **Manager Call:**
    - Бейдж рекомендации (Passed / Rejected / On Hold);
    - **Overview** — общая оценка + сильные/слабые стороны;
    - **Soft Skills** — коммуникация, мотивация, culture fit, зарплатные ожидания, ясность мышления;
    - **Broker Fit** — соответствие требованиям брокера;
    - **Decision** — обоснование рекомендации.

- **Technical:**
    - Бейдж рекомендации (Hire / No Hire / Uncertain);
    - Индикатор уровня + полоска Score (зелёная ≥75, янтарная ≥50, красная <50);
    - **Overview**, **Skills Match**, **Broker Match**, **Decision**.

- **Final Result:**
    - Индикатор Hired / Lost;
    - Сводка по manager call и technical;
    - Итоговая рекомендация.

**Transcript** — сырой транскрипт в моноширинном шрифте.

**CV** — текст извлечённого CV.

**Broker Request** — исходный текст требований клиента.

**Questions** — список вопросов, заданных в ходе интервью, с тэгом «как кандидат ответил»: Well / Partial / Poor.

## Интеграция с Linear

Большая часть интервью анализируется автоматически через webhook Linear. Пользователь работает с тикетами в Linear, а приложение реагирует на хэштеги в комментариях и смены статуса.

> **Порядок действий не важен.** Для запуска анализа должны быть одновременно на месте **нужный статус тикета** и **нужные маркер-комментарии в треде кандидата**. Какое именно из этих двух событий пришло последним — не играет роли: анализ стартует в момент, когда обе части сошлись. Можно сначала сменить статус и потом писать комментарии, или наоборот — результат одинаковый.

### Что нужно для каждой стадии

| Стадия | Статус тикета | Маркеры в треде кандидата |
|---|---|---|
| **Manager call** | `Broker's Call` | **И** reply с `#manager_call_transcript` + транскрипт (ссылка/вложение), **И** reply с `#feedback_manager_call` + текст фидбека (опционально строка `Manager: Имя`). Анализ запустится в момент, когда **последнее** из этих трёх требований выполнится. |
| **Technical** | `Tech Call` | reply с `#technical_call_transcript` + транскрипт. Фидбек не нужен. |
| **Final result** | `Hired` или `Lost` | reply с точным содержимым `#hired` **или** `#lost` в треде кандидата. Маркер работает **индивидуально на кандидата**, а не на весь тикет: в одном тикете могут быть и hired-кандидаты, и lost-кандидаты, каждому поставится финал со своим `decision`. Кандидаты без маркера не анализируются. Плюс у кандидата должен быть хотя бы один предыдущий анализ (manager_call или technical) — иначе финал молча пропускается (суммировать нечего). |

### Что происходит при любом событии на тикете

- **Приходит коммент с маркером** (`#feedback_manager_call`, `#manager_call_transcript`, `#technical_call_transcript`, `#hired`, `#lost`) → приложение перепроверяет **все три стадии** и запускает те, у которых и статус, и маркеры уже на месте (и анализа ещё нет).
- **Меняется статус** на `Broker's Call` / `Tech Call` / `Hired` / `Lost` → тот же самый re-evaluate. Если раньше не хватало только статуса — анализ запустится сейчас.
- **Меняется статус** на `Triage` / `In Progress` / `Client Review` / `On Hold` → внутренний статус синхронизируется, пишется строка в `IncomingRequestStatusHistory` для расчёта Time On Stage, но никакой анализ не запускается.

### Другие реакции на комментарии

| Хэштег / содержимое | Когда срабатывает | Что происходит |
|---|---|---|
| **#feedback** *(без суффикса `_manager_call`)* | Любой статус | Текст комментария записывается как `externalFeedback` тикета (причина отказа со стороны клиента). Попадает в `Top External Reasons` на дашборде. |
| Ссылка `my.visualcv.com` в root-комментарии | Любой статус | Счётчик `cvSentCount` у тикета увеличивается, статус меняется на `cv_sent` (если ещё не дальше по воронке), создаётся/обновляется запись в Pipeline Candidates. |

### Повторный анализ не делается

**По одной паре (тикет × кандидат × стадия) анализ создаётся ровно один раз.** Следствия:

- Редактирование уже существующего маркер-комментария **ничего не делает** — webhook реагирует только на создание комментария, не на правку.
- Удалить и запостить заново маркер — тоже не перезапустит: запись в БД уже есть, срабатывает фильтр «already analyzed».
- Если тот же транскрипт случайно запостили под двумя разными кандидатами в одном тикете — LLM-вызов для второго не делается, используется готовый результат.
- Чтобы реально переделать анализ, надо сначала удалить его через админку (или напрямую в БД), и только потом новое событие (коммент или смена статуса) запустит пересчёт.

### Смена заголовка тикета

Если в заголовке тикета меняется имя клиента (форматы `Role for Company` или `Role - Company`), приложение обновит `clientName` у соответствующего `IncomingRequest` и у всех уже проанализированных интервью в этом тикете. Если в новом заголовке клиента нет — обновление пропускается, старое значение сохраняется.

### Структура треда кандидата в Linear

Каждая ветка комментариев в тикете представляет одного кандидата. Ветка считается «веткой кандидата», если **в root-комментарии есть CV-ссылка** (visualcv) **или в ветке есть хотя бы один хэштег** (`#manager_call_transcript`, `#technical_call_transcript`, `#feedback_manager_call`, `#hired`, `#lost`).

Все маркеры должны быть **replies внутри ветки кандидата**. Корневой комментарий тикета (не привязанный к CV) маркером не считается.

### Типовые ошибки

- **`#feedback` вместо `#feedback_manager_call`** — первый это внешний фидбек по тикету, он не триггерит анализ manager_call.
- **`#hired ok` или `#lost — спасибо`** вместо чистого `#hired`/`#lost` — финальный маркер определяется по **точному совпадению**, любой дополнительный текст ломает распознавание.
- **Маркер в корневом комментарии тикета**, а не в треде кандидата — ветка не распознаётся как кандидатская, маркер игнорируется.
- **Перевод в `Hired`/`Lost` без `#hired`/`#lost`-реплая** — система не понимает, для какого из кандидатов в тикете это решение, и финал не запускает.

## Как считается статистика

Раздел отвечает на вопрос «откуда взялась эта цифра». Полезно, если число на дашборде кажется странным или хочется понять, что именно фильтр периода захватывает.

### Источники данных

В системе три основные таблицы, которые формируют всю аналитику:

| Таблица | Что хранит | Откуда берётся |
|---|---|---|
| **`Interview`** | Каждый AI-анализ (manager_call / technical / final_result). Содержит JSON-поле `analysis` со скором, рекомендацией, сильными/слабыми сторонами, decision breakers, и `questions`. | Создаётся воркером `analyze.worker` по вебхуку Linear или ручному `+ New Analysis`. |
| **`IncomingRequest`** | Один тикет Linear = одна запись. Хранит текущий статус (`triage`, `new`, `in_progress`, `client_review`, `cv_sent`, `manager_call`, `technical`, `hired`, `rejected`/`lost`, `on_hold`, `dropped`), счётчик отправленных CV (`cvSentCount`), внешний фидбек от клиента (`externalFeedback`), `clientName`, `role`. | Upsert при первом вебхуке от Linear, обновляется при смене статуса/title и при `#feedback`-комментах. |
| **`IncomingRequestStatusHistory`** | По одной строке на каждое попадание тикета в новый статус (`status` + `enteredAt`). Используется для расчёта длительности стадий. | Пишется автоматически при upsert и каждом изменении статуса в `IncomingRequest`. |

`Interview` и `IncomingRequest` связаны строкой `linearIssueId` (без FK). Один тикет может иметь несколько `Interview` (по одному на стадию × кандидата).

### Два уровня аналитики

На бэкенде живут **два разных эндпоинта**, которые питают разные блоки UI:

| Эндпоинт | Что считает | На что влияет селектор периода |
|---|---|---|
| `GET /api/interviews/stats` | All-time KPI: `Total Interviews`, `Hire Rate`, `Avg Score`, `Top Role`, разбивка по стадиям и ролям. | **Нет.** Это «пульс системы», период игнорируется. |
| `GET /api/stats/overview?from=&to=` | Всё содержимое вкладок Pipeline и Quality & Insights — Requests, Funnel, Timeline, Quality, Avg Score by Level/Role. | **Да.** Все цифры в этих вкладках считаются только за выбранный диапазон. |

### Что попадает в KPI (верхние карточки)

| Карточка | Формула |
|---|---|
| **Total Interviews** | `count(Interview)` за всё время. В подписи — сколько из них manager_call и technical. |
| **Hire Rate** | Доля `decision = 'hired'` среди интервью со `stage = 'technical'`, всё время. Округляется до целого процента. |
| **Avg Score** | Среднее по `analysis.score` среди технических интервью, всё время. Округляется до целого. |
| **Top Role** | Самая часто встречающаяся `role` в `Interview`. |

> Важно: KPI считает по таблице `Interview` (т.е. по реально проанализированным интервью), а не по тикетам Linear. Тикет, по которому ещё не было анализа, в KPI не виден.

### Что попадает в Pipeline-вкладку

Эндпоинт фильтрует по периоду по двум разным полям:

- `IncomingRequest` — по `receivedAt` (когда тикет создан в Linear).
- `Interview` — по `createdAt` (когда был создан анализ).

Это значит: тикет, открытый в марте, но дошедший до Hired в апреле, в апрельской выборке будет иметь Hired в `pipeline.hired`, но НЕ будет в `requests.total` (его `receivedAt` мартовский).

#### Requests Stats
- `total` = `count(IncomingRequest)` с `receivedAt` в периоде.
- `byStatus` — группировка тех же тикетов по полю `status`.
- `byClient` — по `clientName`.
- `byRole` — по `role`.

#### Pipeline Funnel
- **CV Sent** = тикеты со `status = 'cv_sent'` или `cvSentCount > 0` (заявок, по которым отправили хотя бы одно CV).
- **Total CVs** = сумма `cvSentCount` по тем же тикетам (одна заявка может породить несколько CV).
- **Manager Call / Technical / Final Result** = `count(Interview)` со `stage = …` за период.
- **Hired / Rejected** = `count(Interview)` с `decision = 'hired' / 'rejected'`.
- **On Hold** = `count(IncomingRequest)` со `status = 'on_hold'`.
- **Conversion `Manager Call → Technical`** = `reachedTechnical / reachedManagerCall` × 100.
- **Conversion `Technical → Hired`** = `hired / reachedTechnical` × 100.

#### Time on Stages
- **Длительность каждой стадии** считается из `IncomingRequestStatusHistory`: для каждого тикета берётся время между двумя соседними записями о смене статуса. Незавершённая (текущая) стадия не учитывается — ждём следующего перехода.
- **Avg time from Triage to Hired** — среднее по тикетам, дошедшим до `hired`: `(время входа в hired − время первой записи истории)`.
- **Тренд по месяцам** — `count(Interview)` группой по `YYYY-MM` от `createdAt`.

> Тикеты, созданные **до внедрения трекинга истории** (нет записей в `IncomingRequestStatusHistory`), в средние Time on Stages не попадают.

### Что попадает в Quality & Insights

#### Quality Insights (текстовые кластеры)
- **Rejection reasons** — раскручиваем `analysis.decisionBreakers` (массив строк) по всем `Interview` периода → подаём в `clusterTextItems` → LLM возвращает топ-кластеры с частотой.
- **Weaknesses** — то же самое для `analysis.weaknesses` (фразы `not mentioned` отфильтровываются).
- **External reasons** — `IncomingRequest.externalFeedback` от тикетов периода → LLM-кластеризация.
- **Hire rate by role** — для каждой роли `hired / total` среди технических интервью с этой ролью; сортируется UI'ем.

> Кластеризация — единственное место в дашборде, где **синхронно вызывается LLM** (Qwen). Поэтому первый запрос за новый период идёт дольше (~3-5 с); после этого результат лежит в кэше Redis 30 мин.

#### Avg Score by Level / Role
- Берём `analysis.score` со всех интервью периода, у которых score не пустой.
- Группируем по `level` (Junior / Middle / Senior / Architect) или по `role`.
- Внутри группы — среднее, округлённое до целого.

### Кэширование и Refresh

- Ответ `GET /api/stats/overview` кешируется в Redis по ключу `stats:overview:<from>:<to>` с TTL **30 минут**.
- При создании нового `Interview` бэкенд автоматически инвалидирует **все** ключи `stats:overview:*` (так что после нового анализа дашборд пересчитается на следующем заходе).
- Кнопка **Refresh** в карточке Requests Stats и параметр `?refresh=1` в URL — принудительно удаляют кеш для текущего периода.
- Прямые правки в Postgres (минуя API) **не триггерят** инвалидацию: либо ждать TTL, либо нажать Refresh.

### Что в статистике НЕ учитывается

- **Удалённые тикеты Linear.** Удаление тикета в Linear само по себе не приходит как webhook-событие, и сейчас система его не обрабатывает: запись `IncomingRequest` (и связанные `Interview`) остаётся в БД и продолжает попадать в статистику. Никакого статуса «deleted» в Pipeline или счётчика «создано, но затем удалено» в данный момент нет.
- **Удалённые анализы.** Если интервью удалено через UI (`Delete` в модалке) или эндпоинт `DELETE /api/interviews/:id`, оно физически исчезает из БД и больше нигде в статистике не учитывается. Никакого «soft delete» / архива нет.
- **Дубликаты.** Уникальный индекс `(linearIssueId, parentCommentId, stage)` гарантирует, что одно и то же интервью не попадёт в статистику дважды; повторные триггеры от Linear молча отбрасываются.
- **Тикеты без `linearIssueId`.** Анализы, созданные через ручной `+ New Analysis` без указания Linear ID, есть в `Interview`, но НЕ имеют записи `IncomingRequest`. Они попадают в KPI / Pipeline Funnel / Quality / Avg Scores, но НЕ влияют на Requests Stats и Time on Stages.

## Частые задачи и подсказки

### «Хочу посмотреть, как долго идёт тикет до найма»
Dashboard → вкладка **Pipeline** → блок **Time on Stages**. Верхняя метрика — среднее время от Triage до Hired. Ниже — полоса с разбивкой по стадиям.

> Метрики считаются по тикетам, созданным **после** внедрения трекинга истории статусов. Старые тикеты в эти средние не попадают.

### «Нужно найти все интервью кандидата Ivan Petrov»
Вариант 1: вбить имя в поиск на странице **Candidates** → кликнуть по строке → открыть **Candidate Detail**.
Вариант 2: на странице **Interviews** использовать фильтры по роли/менеджеру/клиенту.

### «Не обновляется статистика на дашборде»
Нажать кнопку **Refresh** в блоке Requests Stats, либо открыть вкладку с параметром `?refresh=1` — сбросит Redis-кэш (TTL у него и так 30 минут).

### «На странице интервью поиск по клиенту не находит»
Поиск регистронезависимый и по подстроке — достаточно ввести часть названия (например, «acme» найдёт «ACME Corp»).

### «Тикет в Linear перешёл в Hired, но анализ не создался»
Проверить по очереди:
1. Есть ли у этого кандидата в его ветке reply с текстом ровно `#hired` (или `#lost` для `Lost`). Если нет — допиши его прямо сейчас: система сама пересмотрит тикет в момент прихода коммента и запустит финал, переводить статус ещё раз не нужно.
2. Есть ли у кандидата хотя бы один предыдущий анализ (manager_call или technical). Если нет — финал не создаётся, суммировать нечего.
3. Распознаётся ли ветка как «ветка кандидата»: в root-комментарии должна быть CV-ссылка или в ветке хотя бы один хэштег. Если CV пришло как вложение без ссылки — продублируй ссылкой в root.
4. Маркер стоит точно `#hired` / `#lost`, без доп. текста, и это **reply** в ветке, а не корневой комментарий тикета.

Если всё на месте и анализ всё равно не появился — обратиться к админу, посмотреть логи webhook.

### «Запустить анализ вручную, когда в Linear ничего нет»
**+ New Analysis** в шапке → заполнить транскрипт и детали → **Start Analysis**.

### «Посмотреть скоры по уровням — сравнить Junior и Senior»
Dashboard → вкладка **Quality & Insights** → карточка **Level Scores**.

### «Причины отказов — что чаще всего встречается»
Dashboard → вкладка **Quality & Insights** → **Decision Breakers** и **External Reasons** (внешний фидбек от клиента).
